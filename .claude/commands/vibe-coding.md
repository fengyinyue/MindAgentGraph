# Vibe Coding 流程

这是一个结构化的 Vibe Coding 开发流程，分 5 个阶段将模糊想法转化为可自动执行的工程任务。
**同时支持从零开始的新项目和已有项目的功能增量开发。**

适用场景：
- 从零开始构建新项目
- 为已有项目添加新功能模块
- 重构已有项目的某个模块
- 为已有项目补充文档和测试

## 核心原则

- **不猜测意图** — 任何不明确的地方都必须向用户提问澄清
- **模块独立** — 模块与模块之间尽量保持相互独立，可独立测试
- **测试完备** — 代码必须有完整的 pytest 单元测试
- **质量门禁** — 代码必须通过 mypy 类型检查和 ruff 代码规范检查
- **最终自动化** — Prompt 阶段的输出可直接由主 Agent + 子 Agent 自动执行，无需人工参与

---

## 阶段 0：已有项目分析（仅已有项目需要）

当用户在一个**已有代码**的项目中请求开发新功能时，必须先执行此阶段。
如果是全新项目，跳过此阶段，直接从阶段 1 开始。

**输入：** 项目根目录
**输出：** `doc/existing-codebase.md`（项目现状分析文档）

**执行步骤：**

1. **盘点现有资产：**
   - 列出项目文件结构（src/、tests/、doc/ 等）
   - 读取 `pyproject.toml` / `package.json` / `Cargo.toml` 等，了解依赖和工具链
   - 读取现有的 CLAUDE.md 或 README.md，了解项目背景
2. **分析现有架构：**
   - 识别现有模块划分和目录结构
   - 分析模块间的依赖关系
   - 了解已有的设计模式和技术选型
3. **评估现有测试和代码质量：**
   - 检查 pytest / mypy / ruff 的现有配置
   - 运行现有测试，确认基线通过
   - 评估代码风格和测试覆盖率
4. **确定改造策略：**
   - 新增功能是独立模块还是需要修改现有模块
   - 新增功能需要遵循的现有约定（命名、目录结构、测试风格）
   - 可能需要重构的现有代码
5. 生成 `doc/existing-codebase.md`，包含：
   - 项目概述和技术栈
   - 现有模块清单及职责
   - 现有测试和质量门禁配置
   - 新增功能的集成策略建议

**重要：** 分析过程中如有任何不确定的地方（如不熟悉的框架、不清楚的模块职责、命名歧义等），必须向用户提问确认。

## 阶段 1：需求文档

**输入：** 用户的一句话目标描述
**输出：** `doc/proposal.md`

**执行步骤：**

1. 了解用户的目标（如："我想用 Python 开发一个番茄钟"）
2. **不预设任何知识** — 如果对领域知识不了解，先通过提问帮助用户梳理
3. 使用提问的方式逐一确认需求，包括但不限于：
   - 核心功能范围
   - 用户交互方式（CLI / GUI / Web）
   - 数据存储需求
   - 配置与自定义选项
   - 边界条件和异常处理
4. 汇总确认结果，写入 `doc/proposal.md`，包含：
   - 项目概述
   - 目标用户
   - 功能需求列表
   - 非功能需求
   - 约束条件

**重要：** 不要猜测任何需求细节，所有不明确的地方逐一向用户提问确认。

---

## 阶段 2：概要设计文档

**输入：** `doc/proposal.md`（+ 已有项目时额外读取 `doc/existing-codebase.md`）
**输出：** `doc/high-level-design.md`

**执行步骤：**

1. 通读需求文档，理解全部需求
2. **已有项目：** 阅读 `doc/existing-codebase.md`，了解现有架构、模块和技术约定
3. 根据需求划分出功能模块
4. 识别模块与模块之间的关系（依赖、数据流、调用关系）
5. **已有项目：** 明确新增模块与现有模块的关系，标出需要修改的现有模块
6. 生成 `doc/high-level-design.md`，包含：
   - 模块划分及每个模块的职责
   - 模块间关系图（文字描述或 mermaid 图）
   - 数据流说明
   - 技术选型（语言、框架、库）— 已有项目应沿用现有技术栈
   - 整体架构风格（如分层架构、插件式等）
   - **已有项目附加：** 新增/修改模块标注、现有架构兼容性说明

**重要：** 如果需求文档中有任何模糊之处，必须回问用户确认后再继续。

---

## 阶段 3：详细设计文档

**输入：** `doc/proposal.md`（+ 已有项目时额外参考 `doc/existing-codebase.md`）
**输出：** `doc/detailed-design.md`

**执行步骤：**

1. 基于概要设计的模块划分，为每个模块编写详细设计
2. **已有项目：** 标注哪些模块是新增、哪些是修改现有代码，修改现有模块时写明变更范围和向后兼容策略
3. 每个模块需包含：
   - 模块职责描述
   - 对外接口（函数签名、类定义）
   - 内部数据结构
   - 关键算法或逻辑说明
   - 错误处理策略
   - 配置项
4. 模块间尽量保持独立，便于独立测试
5. 生成 `doc/detailed-design.md`

**重要：** 设计过程中如有任何不明确的地方，必须向用户提问。

---

## 阶段 4：任务拆分

**输入：** `doc/proposal.md` + `doc/detailed-design.md`（+ 已有项目时额外参考 `doc/existing-codebase.md`）
**输出：**
- `doc/tasks/<module-name>.md` — 每个模块一个任务文件
- `doc/tasks/progress.md` — 总体进度跟踪文件

**执行步骤：**

1. 根据详细设计中的模块划分，为每个模块创建一个独立的任务文件
2. **已有项目：** 额外创建 `doc/tasks/existing-modifications.md` 记录需要修改的现有文件清单
3. 每个 `<module-name>.md` 包含：
   - 模块名称和概述
   - 最小可执行子任务列表（用 checkbox `- [ ]` 表示）
   - **已有项目：** 新增任务和修改任务用标签区分（如 `[新增]` / `[修改]`）
   - 每个子任务有清晰的验收标准
   - 子任务粒度：每个任务应可在单次 Vibe Coding 会话中完成
4. `progress.md` 包含：
   - 所有模块的完成状态（用 checkbox 表示）
   - 整体项目进度概览
   - 模块间依赖关系提醒
   - **已有项目：** 现有模块不受影响的部分标注为 N/A

**重要：** 子任务拆分时如有任何不明确的地方，必须向用户提问。

---

## 阶段 5：生成 Vibe Coding Prompt

**输入：** `doc/proposal.md` + `doc/detailed-design.md` + `doc/tasks/`（+ 已有项目时额外参考 `doc/existing-codebase.md`）
**输出：** `doc/prompt.md`

**执行步骤：**

1. 阅读所有输入文档，全面了解工程目标、架构、模块划分和任务
2. **已有项目：** 阅读 `doc/existing-codebase.md`，确保 Prompt 中包含足够的现有代码上下文
3. 生成一个完整的起始 Prompt，包含以下角色定义：

   **主 Agent 职责：**
   - 读取 `progress.md` 跟踪整体进度
   - 按依赖顺序为每个模块派生子 Agent
   - 检查子 Agent 输出，更新进度文件
   - 运行集成测试，确保模块间协作正常
   - 运行全量 mypy 和 ruff 检查
   - **已有项目：** 确保新增代码不破坏现有测试，现有模块的修改通过了回归测试

   **子 Agent 职责：**
   - 根据 `<module-name>.md` 实现对应模块
   - **已有项目：** 先阅读 `doc/existing-codebase.md` 了解现有约定，然后实现
   - 编写完整的 pytest 单元测试
   - 确保测试全部通过
   - 确保代码通过 mypy 和 ruff 检查
   - 完成后回报主 Agent

4. Prompt 中明确要求：
   - 整个过程不需要人工参与
   - 代码必须有完整的 pytest 单元测试
   - 代码必须通过 mypy 和 ruff 检测
   - 使用 uv 作为包管理器运行测试和检查
   - **已有项目：** 必须遵循现有代码风格和目录结构约定

**重要：** 生成 Prompt 过程中，如有任何不明确的地方必须向用户提问。

## 使用方式

支持两种模式，用户可随时从任一阶段切入。

### 模式 A：全新项目

```
# 从零开始
/vibe-coding 我想用 Python 开发一个 XXX

# 已有需求文档，从概要设计开始
/vibe-coding 基于 doc/proposal.md 生成概要设计

# 已有全部设计文档，直接生成 Prompt
/vibe-coding 基于现有文档生成执行 Prompt
```

### 模式 B：已有项目增量开发

```
# 为已有项目添加新功能（自动执行阶段 0 → 阶段 1）
/vibe-coding 为这个项目添加一个 XXX 功能

# 先只分析现有代码，不进入设计
/vibe-coding 先分析这个项目的现状

# 基于现有代码分析和需求文档，生成概要设计
/vibe-coding 基于 doc/proposal.md 和 doc/existing-codebase.md 生成概要设计

# 已有全部文档，直接生成执行 Prompt
/vibe-coding 基于所有现有文档生成执行 Prompt
```

## 文件结构总览

```
project/
├── doc/
│   ├── proposal.md              # 阶段 1：需求文档
│   ├── existing-codebase.md     # 阶段 0：项目现状分析（仅已有项目）
│   ├── high-level-design.md     # 阶段 2：概要设计
│   ├── detailed-design.md       # 阶段 3：详细设计
│   ├── prompt.md                # 阶段 5：执行 Prompt
│   └── tasks/
│       ├── progress.md          # 阶段 4：总体进度
│       ├── existing-modifications.md  # 阶段 4：现有文件修改清单（仅已有项目）
│       └── <module>.md          # 阶段 4：模块任务清单
└── src/                         # 已有代码 + 由 Prompt 阶段新增的代码
    └── ...
```
